# Телеграм-бот автошколы — развёртывание

Бот живёт на Cloudflare Workers, данные — в Cloudflare D1. Всё ниже делается
один раз, по порядку, из каталога `bot/`.

Нужно заранее: аккаунт Cloudflare, установленный `npm`, аккаунт Telegram.

```bash
cd bot
npm install
npx wrangler login
```

---

## 1. Создать бота у @BotFather

В Telegram напишите [@BotFather](https://t.me/BotFather):

1. `/newbot`
2. Имя бота (видит ученик) — например `Автошкола Тбилиси`.
3. Username — должен заканчиваться на `bot`, например `avtoshkola_tbilisi_bot`.

BotFather пришлёт **токен** вида `1234567890:AA...`. Это пароль от бота —
не коммитить, не пересылать. Понадобится в шаге 4.

Там же полезно выключить приватность, чтобы бот видел команды в группе:
`/setprivacy` → выбрать бота → `Disable`.

---

## 2. Создать базу D1

```bash
npx wrangler d1 create avtoshkola-bot
```

Команда напечатает блок с `database_id`. Скопируйте это значение в
`wrangler.toml`, заменив `REPLACE_AFTER_WRANGLER_D1_CREATE`:

```toml
[[d1_databases]]
binding = "DB"
database_name = "avtoshkola-bot"
database_id = "сюда-вставить-выданный-id"
```

---

## 3. Развернуть таблицы

```bash
npx wrangler d1 migrations apply avtoshkola-bot --remote
```

`--remote` обязателен: без него миграции применятся к локальной копии, а
боевая база останется пустой.

> **Перед накатом на базу с заявками сделайте экспорт.** Миграция
> `0002_leads_status_check.sql` пересобирает таблицу `leads` целиком — SQLite
> не умеет добавлять ограничение к существующей таблице:
>
> ```bash
> npx wrangler d1 export avtoshkola-bot --remote --output leads-backup.sql
> ```
>
> На пустой базе первого развёртывания экспортировать нечего — шаг можно
> пропустить.

## 4. Задать токен и два секрета вебхука

```bash
npx wrangler secret put BOT_TOKEN
# вставить токен из шага 1
```

Секретов у вебхука **два, и это две разные строки**. Сгенерируйте их
случайными, двумя отдельными запусками команды — не придумывайте руками:

```bash
openssl rand -hex 32   # это WEBHOOK_PATH_SECRET
openssl rand -hex 32   # запустить ВТОРОЙ раз, это WEBHOOK_HEADER_SECRET
```

Получатся две несовпадающие строки по 64 символа. Запишите, где какая:

```bash
npx wrangler secret put WEBHOOK_PATH_SECRET
# вставить ПЕРВУЮ строку — она будет видна в адресе вебхука

npx wrangler secret put WEBHOOK_HEADER_SECRET
# вставить ВТОРУЮ строку — она уходит только в заголовке запроса
```

> **Почему строки обязаны различаться.** Секрет пути рано или поздно
> утекает — адреса оседают в логах прокси, в Logpush, в аналитике HTTP; с
> заголовками такого не происходит. Заголовок и нужен, чтобы пережить эту
> утечку, — но если вписать в оба поля одну и ту же строку, то утечка адреса
> выдаст и её, и второй рубеж перестанет существовать.

Сохраните обе строки — они понадобятся в шаге 7, каждая в своём поле.

Если хотя бы один из двух секретов не задан, воркер отвечает 404 на любой
запрос (вебхук не работает вовсе), а в `npx wrangler tail` пишет, какого
именно секрета не хватает.

Оставшиеся два значения (`ADMIN_CHAT_ID`, `ADMIN_IDS`) задаются в шаге 5,
когда появится группа.

> **Почему `wrangler secret put`, а не `[vars]` в `wrangler.toml`.**
> Блок `[vars]` при каждом `deploy` перезаписывает то, что выставлено в
> дашборде Cloudflare. Placeholder вернулся бы после любого деплоя, и бот
> молча перестал бы слушаться администраторов. Через `secret put` значение
> живёт в одном месте и деплоем не затрагивается.

## 5. Создать закрытую группу администраторов и узнать её ID

1. В Telegram: новая группа → добавить туда бота из шага 1.
2. Дайте боту права администратора группы (иначе он не увидит команды).
3. Напишите в группе любое сообщение.
4. Узнайте ID группы. Пока вебхук ещё не установлен (шаг 7), это делается так:

```bash
curl "https://api.telegram.org/bot<ТОКЕН>/getUpdates"
```

В ответе найдите `"chat":{"id":-1001234567890,...}`. ID группы —
отрицательное число, обычно начинается с `-100`. Скопируйте его целиком,
вместе с минусом.

Свой собственный Telegram ID (число, положительное) можно узнать там же в
поле `"from":{"id":...}` или у бота [@userinfobot](https://t.me/userinfobot).

Теперь задайте оба значения:

```bash
npx wrangler secret put ADMIN_CHAT_ID
# вставить ID группы, например -1001234567890

npx wrangler secret put ADMIN_IDS
# Telegram ID администраторов через запятую, например: 111111111,222222222
```

Права проверяются по двум условиям сразу: сообщение пришло из группы
`ADMIN_CHAT_ID` **и** отправитель есть в `ADMIN_IDS`. Одного мало.

Пока не заданы все четыре значения (два секрета вебхука и эти два), бот
отвечает 404 на любой запрос, а причину пишет в `npx wrangler tail`. Это
намеренно: с пустым `ADMIN_CHAT_ID` бот принимал бы анкеты и отвечал ученику
«Заявка отправлена», а карточка уходила бы в несуществующий чат. Шумный
отказ лучше, чем тихо теряемые заявки.

> **Кто видит телефоны учеников.** Как только администратор нажимает
> «Взять в работу», в карточке заявки открывается номер телефона ученика —
> и его видит **любой участник группы**. Поэтому в этой группе должны быть
> только сотрудники школы. Никаких учеников, знакомых и подрядчиков.

## 6. Выложить бота

```bash
npm run deploy
```

Команда сначала пересобирает базу знаний (`npm run build-kb`) из
`baza-znaniy/dlya-bota/*.txt`, потом деплоит воркер. В конце она напечатает
адрес вида `https://avtoshkola-bot.<ваш-поддомен>.workers.dev` — он нужен
в шаге 7.

## 7. Подключить вебхук Telegram

Подставьте свои значения: `<ТОКЕН>` из шага 1, оба секрета из шага 4,
`<АДРЕС>` из шага 6. Не перепутайте их местами.

```bash
curl -X POST "https://api.telegram.org/bot<ТОКЕН>/setWebhook" \
  -H "Content-Type: application/json" \
  -d '{
    "url": "https://<АДРЕС>/webhook/<WEBHOOK_PATH_SECRET>",
    "secret_token": "<WEBHOOK_HEADER_SECRET>",
    "max_connections": 1,
    "allowed_updates": ["message", "callback_query"]
  }'
```

Это два независимых рубежа, и потому две разные строки: в адресе —
`WEBHOOK_PATH_SECRET`, в заголовке `X-Telegram-Bot-Api-Secret-Token` —
`WEBHOOK_HEADER_SECRET`. Воркер проверяет оба: не тот путь — 404, не тот
заголовок (или заголовка нет) — 403.

Ответ должен быть `{"ok":true,...}`.

---

## 8. Проверить, что всё работает

```bash
curl "https://api.telegram.org/bot<ТОКЕН>/getWebhookInfo"
```

Смотрите в ответе:

- `"url"` — ваш адрес вебхука;
- `"pending_update_count": 0` — очередь не копится;
- `"last_error_message"` — этого поля быть не должно. Если оно есть, читайте
  текст. Код подсказывает, где ошибка: `404` — не совпал
  `WEBHOOK_PATH_SECRET` в адресе (либо какой-то из двух секретов вообще не
  задан, см. `wrangler tail`), `403` — не совпал `WEBHOOK_HEADER_SECRET`
  в `secret_token`.

Затем живая проверка:

1. Напишите боту в личку `/start` — должно прийти меню.
2. Нажмите «Записаться», пройдите анкету до «Согласен».
3. В группе администраторов должна появиться карточка заявки с кнопкой
   «Взять в работу».
4. В группе наберите `/zayavki` — бот покажет последние заявки.

Живые логи, если что-то пошло не так:

```bash
npx wrangler tail
```

## Команды в группе администраторов

Работают только в группе `ADMIN_CHAT_ID` и только у тех, кто есть в
`ADMIN_IDS`. В личке боту они не отвечают — ни администратору, ни кому-либо ещё.

| Команда | Что делает |
|---|---|
| `/set дата_группы 15 сентября` | меняет дату ближайшей группы, которую видит ученик |
| `/zayavki` | последние десять заявок со статусами |
| `/resend` | досылает карточки заявок, которые не ушли в группу |
| `/release 12` | снимает исполнителя с заявки №12 |
| `/card 12` | высылает карточку заявки №12 в группу заново |

Имя бота командам не мешает: `/release@ваш_бот 12` работает так же, как
`/release 12`.

### Когда нужна `/release`

Заявку берёт администратор, и дальше только он может нажать «Позвонил»,
«Закрыть» и «Освободить». Если этот человек уволился и его убрали из
`ADMIN_IDS` — или он просто взял заявку и пропал, — заявка застревает: она
занята, а нажать по ней уже некому.

`/release 12` снимает исполнителя и возвращает заявку в общий доступ: её
может взять любой администратор. Кто и с кого снял заявку, остаётся в
истории — это отдельное событие, не то же самое, что человек освободил
свою заявку сам.

Отказ придёт в двух случаях, и в ответе будет написан текущий статус:
заявка и так свободна (снимать некого) или она уже закрыта. Закрытые заявки
командой не переоткрываются.

### Когда нужна `/card`

Карточку заявки могли удалить из группы — вместе с ней пропали и кнопки.
`/resend` тут не поможет: он досылает только те карточки, которые вообще
не дошли. `/card 12` высылает карточку заново в любом случае.

Старая карточка, если она где-то выше ещё висит, не удаляется, но новая
помечена: «прежняя карточка устарела — нажимайте кнопки в этой». Нажатие на
старую ничего не сломает, просто она больше не обновляется.

## Как добавить нового администратора потом

`ADMIN_IDS` — это один список через запятую, он перезаписывается целиком,
а не дополняется. Поэтому вводите **всех** администраторов сразу, включая
существующих:

```bash
npx wrangler secret put ADMIN_IDS
# было:  111111111,222222222
# стало: 111111111,222222222,333333333
```

Изменение применяется сразу, деплой не нужен.

Не забудьте также добавить нового человека в саму группу — без этого одного
`ADMIN_IDS` мало (проверяются оба условия).

Чтобы убрать администратора: уберите его ID из списка **и** удалите его из
группы.

## Очереди и ежедневная уборка

Минутный cron обрабатывает durable inbox и outbox. Ночной cron в 03:00 UTC
дополнительно запускает cleanup. Webhook отвечает 200 только после сохранения
update в D1. Настройка `max_connections: 1` уменьшает переупорядочивание в
Telegram, но дедупликация `update_id` и запрет обгона работают независимо от нее.

| Что | Когда удаляется |
|---|---|
| записи дедупликации апдейтов | через 7 дней |
| raw inbox и брошенные анкеты | не дольше 24 часов |
| audit и command results | 180 дней и 24 часа соответственно |
| завершенный outbox | через 30 дней, абсолютный предел 180 дней |
| контакты в заявке | через 90 дней после закрытия, в любом случае — через 180 дней после создания |

«Контакты» — это телефон, имя, текст вопроса и chat_id ученика: вместе они
так же однозначно указывают на человека, как один телефон, а chat_id ещё и
позволяет ему написать. Сама строка заявки остаётся — по ней считается
статистика, и на неё ссылается журнал.

## Мониторинг inbox и outbox

Проверяйте Worker logs и D1 не реже одного раза в рабочий день. Запросы ниже
не возвращают имя, телефон или текст анкеты:

```sql
SELECT state, count(*) AS count, min(created_at) AS oldest
FROM inbox WHERE state != 'done' GROUP BY state;

SELECT state, count(*) AS count, min(created_at) AS oldest
FROM outbox WHERE state IN ('pending','sending','failed','manual_contact')
GROUP BY state;
```

Нормальное состояние: нет `failed`, `manual_contact` разобраны сотрудником,
а `oldest` для pending не старше нескольких минут. Рост attempts, lag больше
пяти минут или просроченный sending lease требуют просмотра `wrangler tail`.
Ошибка одного update не теряется: payload хранится до 24 часов и повторяется
по расписанию 1, 5, 15, 60 минут, затем раз в час. События одного chat_id не
обгоняют самое раннее незавершенное событие.

`sent` означает успешный ответ Telegram API, но не прочтение человеком.
Crash после ответа Telegram и до D1 commit может дать повтор сообщения.
Exactly-once для внешней доставки не заявляется. Повтор доставки не повторяет
доменное confirm/decline действие.

## Staging, backup и восстановление

Staging использует отдельные Worker, D1, Telegram bot и Access audience.
Production export нельзя импортировать в локальные UI tests. Перед каждой
production migration сделайте export, а ежедневный зашифрованный backup
храните не дольше 7 дней. Цели: RPO не больше 24 часов, RTO не больше 60 минут.

Порядок восстановления:

1. Создать изолированную D1 из выбранного backup или Time Travel.
2. Не подключать cron, webhook и пользовательские hostnames.
3. Сравнить counts и стабильные IDs groups/bookings с контрольным отчетом.
4. Запустить cleanup на восстановленной копии до открытия доступа.
5. Оставить outbox остановленным, проверить старые pending/sending вручную и
   пометить недействительные события superseded. Не рассылать backup повторно.
6. Только после сверки переключить binding и включить cron/webhook.

Факт репетиции, время RTO и возраст backup записываются отдельно. Этот runbook
не является разрешением на production restore.

## Cutover и rollback групповых записей

Новый writer включается только секретом `BOOKING_ENABLED=true`. До включения
задайте `BOOKING_SECRET`, `BOOKING_ALLOWED_ORIGINS`, `TURNSTILE_SECRET`,
`ACCESS_TEAM_DOMAIN`, `ACCESS_AUD`, `ACCESS_ALLOWED_EMAILS`, `ADMIN_ORIGIN` и
проверьте Access, staging D1, inbox/outbox и тестового Telegram bot.

Клиенты получают адреса отдельно от Worker secrets:

- в `index.html` и `voprosy/index.html` у загрузчика `js/main.js` заполнить `data-booking-api` полным
  origin Worker без завершающего `/`, а `data-turnstile-sitekey` публичным
  site key Turnstile;
- на VPS задать `BOOKING_API_URL` тем же origin Worker для read-only списка;
- на VPS задать `BOOKING_ADMIN_URL` полным адресом `<origin Worker>/admin/`,
  чтобы прежняя Python-админка вела в новый интерфейс;
- `ADMIN_ORIGIN` в Worker должен точно совпадать с origin новой админки.

Пустой `data-booking-api` оставляет новый интерфейс записи выключенным. Это
безопасное состояние до cutover, а не production настройка.

### Автоматическое пополнение расписания

Без отдельной настройки расписание остается ручным. После применения миграции
`0005_rolling_schedule.sql` автоматический режим включается только точным
значением `true`:

```bash
npx wrangler secret put ROLLING_SCHEDULE_ENABLED
# ввести: true
```

Минутный cron использует тот же `BOOKING_SECRET`, атомарные команды и журнал
изменений. По умолчанию он поддерживает три будущие предварительные группы от
якоря `2026-10-05`: каждые 14 дней, в `19:00` Asia/Tbilisi, по 12 мест.
Подтверждение места и старта остается ручным. Перенесенная или отмененная
календарная позиция сохраняется и автоматически не создается заново.

Подтвержденные значения можно задать явно тем же способом:

```bash
npx wrangler secret put ROLLING_SCHEDULE_ANCHOR_DATE
# 2026-10-05
npx wrangler secret put ROLLING_SCHEDULE_START_TIME
# 19:00
npx wrangler secret put ROLLING_SCHEDULE_CAPACITY
# 12
```

Неверное или частичное значение останавливает только эту cron-задачу с ошибкой
`scheduled_failed:rolling_schedule`; группы при этом не меняются частично.
Флаг не открывает public/admin API и не заменяет `BOOKING_ENABLED` или Access.
Для возврата к ручному режиму сохраните `ROLLING_SCHEDULE_ENABLED=false`.

Cutover выполняется в одном окне:

1. Сделать D1 export и проверить свежесть backup.
2. Накатить миграции, оставив `BOOKING_ENABLED` выключенным.
3. Проверить public GET, admin auth и синтетическую запись в staging.
4. Отключить старые writers дат: `/set дата_группы` и Python save_group.
5. Отключить FormSubmit перед включением Worker POST, чтобы не было dual-send.
6. Включить `BOOKING_ENABLED=true`, затем проверить три reader и три канала
   записи на синтетических данных.

Перед rollback остановить новый прием на сайте и в Telegram, дождаться пустого
inbox и завершить либо явно отменить активные conversations. Затем выключить
`BOOKING_ENABLED` и вернуть сайт на состояние до cutover. Эта настройка также
закрывает admin API, поэтому новые bookings до повторного открытия проверяются
сотрудником только через защищенный ручной доступ к D1. Не переносить их в
legacy leads автоматически и не включать два writer одновременно. Outbox
остановить до сверки, уже выполненные бизнес-команды не повторять кнопкой
доставки.

## Ограничения потока заявок

Анкету может пройти любой пользователь Telegram, поэтому:

- **не больше трёх заявок с одного чата за сутки.** Четвёртой бот отвечает
  телефоном школы. Живому человеку трёх хватает с запасом (заявка, «ой, не
  тот телефон», ещё одна на всякий случай), скрипту — нет;
- **`/resend` досылает пачками по 25.** В ответе написано, сколько осталось
  в очереди, — повторите команду. Без потолка команда перебирала бы всю
  очередь в одном запросе и на большой очереди упиралась бы в лимиты
  воркера, то есть ломался бы ровно тот инструмент, которым очередь и
  разгребают.

## Обновление базы знаний

Тексты ответов лежат в `baza-znaniy/dlya-bota/*.txt`. После правки:

```bash
npm run deploy
```
