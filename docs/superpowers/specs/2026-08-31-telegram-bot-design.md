# Telegram-бот автошколы: запись на занятия и актуальная информация

Дата: 2026-08-31. Статус: дизайн согласован (ревью-правки от 2026-08-31 внесены), ждёт финального ревью.

## Цель

Бот в Telegram для учеников автошколы (avtoshkola.ge):

1. Отвечает на типовые вопросы (цены, документы, экзамены, контакты) из подготовленной базы знаний `baza-znaniy/`.
2. Принимает заявки на запись — пошаговая анкета.
3. Передаёт заявки команде: несколько администраторов видят их в закрытой Telegram-группе и разбирают, не мешая друг другу.
4. Выдаёт актуальные данные, которые часто меняются (дата набора ближайшей группы), без правки репозитория и деплоя.

## Стек

- TypeScript
- Cloudflare Workers (webhook от Telegram Bot API)
- Cloudflare D1 — единственное хранилище v1: заявки, статусы, история,
  состояние анкеты, динамические факты, дедупликация webhook-обновлений.
  KV в v1 не подключаем: он eventual-consistent (после записи другой запрос
  может до ~60 с видеть старое значение), что опасно для пошагового диалога.
- Claude API — второй уровень ответов на свободные вопросы (подключается **после** проверки основного сценария, не в первом релизе)
- Wrangler — деплой и секреты (`wrangler secret put` для токена бота и ключа API)

## Архитектура

```
Ученик → Telegram-бот → меню или вопрос
                         ├─ готовый ответ из базы (v1)
                         ├─ ИИ с ограниченной базой знаний (v2)
                         └─ форма записи (v1)
                                ↓
                         заявка сохраняется в D1
                                ↓
                     закрытая группа администраторов
                                ↓
        «Взять» → «Позвонил» → «Закрыть» (или «Освободить»)
```

Один Worker, один webhook-эндпоинт. Секретный путь webhook + проверка
`X-Telegram-Bot-Api-Secret-Token`, чтобы посторонние не слали фейковые обновления.

### Идемпотентность webhook

Telegram повторяет webhook при неуспешном HTTP-ответе, поэтому:

- Каждый `update_id` сохраняется в D1 (таблица `processed_updates`,
  `INSERT OR IGNORE`); уже виденное обновление подтверждается ответом 200
  и не обрабатывается повторно.
- Создание заявки идёт с уникальным `submission_id` (генерируется при старте
  анкеты, уникальный индекс в `leads`) — повтор доставки не создаёт дубль.
- Callback-кнопки идемпотентны: повторное нажатие / повторная доставка
  не меняет статус второй раз (условные UPDATE, см. ниже) — бот отвечает
  «уже сделано».
- Старые записи `processed_updates` чистятся по возрасту.

### Время

Всё время в D1 — UTC. В сообщениях пользователям и админам — `Asia/Tbilisi`.

## Компоненты

### 1. Меню и ответы из базы (v1)

- `/start` → приветствие + кнопки: «💰 Цены», «📄 Документы», «🎓 Экзамены»,
  «📅 Ближайшая группа», «📝 Записаться», «📞 Контакты».
- Тексты ответов генерируются из `baza-znaniy/*.md` на этапе сборки —
  один источник правды с сайтом. Обновление стабильного контента:
  правка markdown → `wrangler deploy`.
- Свободный текст вне кнопок (v1, до ИИ): поиск по ключевым словам в базе;
  не нашёл — честный ответ «не знаю, но могу записать вас или дать контакт
  администратора» + кнопки «Записаться» / «Контакты». Бот **никогда не выдумывает**
  ответов о ценах и правилах.
- Любой пользовательский текст экранируется перед вставкой в HTML-разметку
  Telegram (`&`, `<`, `>`), где бы он ни показывался — в карточках заявок,
  эхо-подтверждениях, `/zayavki`.

### 2. Динамические факты (v1)

Таблица `facts` в D1: `key`, `value`, `updated_at`, `updated_by`.
Первый факт: `next_group_date` — дата набора ближайшей группы.

- Ученик: кнопка «📅 Ближайшая группа» → значение из D1.
- Админ: команда `/set дата_группы 15 сентября` прямо в админ-группе.
  Изменение мгновенное, без деплоя. В ответ бот показывает старое и новое
  значение: «дата_группы: „1 сентября“ → „15 сентября“».
- Структура расширяемая: позже можно добавить другие меняющиеся факты
  (акции, свободные места). Отдельная админ-страница-редактор — не сейчас (YAGNI),
  архитектура её не блокирует.

### 3. Форма записи (v1)

Пошаговая анкета. Состояние — таблица `conversations` в D1:
`chat_id` (PK), `step`, `data` (JSON), `submission_id`, `expires_at`.
Просроченные состояния (старше ~1 часа) считаются истёкшими и чистятся.

1. Имя
2. Телефон (кнопка «поделиться контактом» + ручной ввод с валидацией)
3. Что интересует (категория, теория/практика, вопрос — свободный текст)
4. **Согласие на обработку телефона** — явная кнопка «Согласен» перед отправкой.
   Без согласия заявка не создаётся.

После подтверждения: заявка в D1 (`leads`) → карточка в админ-группу.

Таблица `leads`: `id`, `submission_id` (UNIQUE), имя, телефон, вопрос,
`status`, `assigned_to` (ID и имя админа), `chat_id` ученика,
`telegram_message_id` карточки, `delivery_status`, `created_at`, `updated_at`.
История переходов статусов — таблица `lead_events`.

**Хранение телефонов:** телефон нужен только чтобы связаться. Через 90 дней
после закрытия заявки телефон в `leads` затирается (маскируется), остальная
запись остаётся для статистики. Чистка — cron-триггер Workers раз в сутки.

### 4. Админская группа и статусы (v1)

Статусы заявки: `new → in_progress → contacted → closed`.
Плюс возврат `in_progress → new` («Освободить»).

Каждая заявка — сообщение-карточка в закрытой группе с inline-кнопками
по текущему статусу:

- `new`: **«Взять в работу»**.
- `in_progress` (в карточке — имя взявшего): **«Позвонил»**, **«Закрыть»**,
  **«Освободить»**. Телефон ученика показывается обычным текстом в карточке
  после взятия — мобильный клиент сам делает номер кликабельным.
  `tel:`-ссылок в inline-кнопках нет: Bot API гарантирует в кнопках только
  HTTP и `tg://`.
- `contacted`: **«Закрыть»**, **«Освободить»**.
- `closed`: кнопок нет, карточка помечена выполненной.

Правила:

- «Взять в работу» — атомарно, одним условным запросом:

  ```sql
  UPDATE leads
  SET status = 'in_progress', assigned_to = ?
  WHERE id = ? AND status = 'new';
  ```

  Успех — по числу изменённых строк. Два админа физически не могут забрать
  одну заявку; проигравший получает «заявку уже ведёт …».
- «Позвонил», «Закрыть», «Освободить» доступны только назначенному
  администратору; остальным — ответ «заявку ведёт …». (Тоже условные UPDATE
  с проверкой `assigned_to` и текущего статуса — это же даёт идемпотентность.)
- «Освободить» возвращает заявку в `new` — забытая заявка не остаётся
  занятой навсегда, её может взять другой.
- После каждого действия бот редактирует карточку (статус, кто ведёт, кнопки).

### 5. Доступ и безопасность (v1)

Двойная проверка на каждом админском действии:

- callback/команда пришла из чата с ID == `ADMIN_CHAT_ID` (закрытая группа), **и**
- Telegram ID отправителя есть в списке админов (переменная окружения / таблица в D1).

Обычный пользователь не может вызвать админ-команды, увидеть чужие заявки
или телефоны — даже если узнает названия команд. Команды `/zayavki`
(последние заявки со статусами), `/set`, `/resend` работают только в админ-группе.

Новому сотруднику дать доступ = добавить в группу + внести его ID в список.

### 6. Доставка карточек в группу

- В `leads` — `delivery_status` (`pending` / `delivered`) и
  `telegram_message_id` карточки.
- Отправка карточки не удалась (Telegram недоступен, бот удалён из группы) —
  заявка остаётся в D1 со статусом доставки `pending`, ученику всё равно
  подтверждаем приём.
- Команда `/resend` в админ-группе повторно отправляет все `pending`-карточки.
  `/zayavki` показывает недоставленные отдельной пометкой.

### 7. ИИ-слой (v2 — после проверки основного сценария)

- Свободный вопрос, на который не нашлось ответа по ключевым словам →
  Claude API (Haiku), системный промпт = база знаний + правила из
  `baza-znaniy/07-pravila-otvetov-bota.md`.
- Жёсткое правило: нет подтверждённого факта в базе → не придумывать,
  предлагать связаться с администратором или оставить заявку.
- Стоимость — оценить на этапе реализации v2: зависит от размера базы
  в промпте и актуальных цен API.

## Обработка ошибок

- Ошибка отправки в группу → см. «Доставка карточек»: заявка не теряется.
- Невалидный телефон → просим ввести ещё раз, максимум понятных подсказок.
- Истёкшее состояние анкеты → вежливое «начнём заново» + `/start`.
- Ошибки Worker логируются (`wrangler tail` / Workers Logs).

## Тестирование

- Unit: парсинг команд, валидация телефона, машина состояний анкеты,
  генерация ответов из базы, проверка прав админа, экранирование HTML,
  условные UPDATE статусов и идемпотентность (vitest + локальная D1).
- Интеграционно: локальный запуск `wrangler dev` + фейковые Telegram-обновления
  (JSON-фикстуры webhook'а), включая повторную доставку одного `update_id`
  и двойное нажатие callback.
- Ручная приёмка: тестовый бот + тестовая группа до переключения на боевого.

## Рамки первого релиза (v1)

Меню + ответы из базы, динамическая дата набора, форма записи с согласием,
D1-заявки с атомарными статусами и идемпотентным webhook, админ-группа
с кнопками «Взять/Позвонил/Закрыть/Освободить», контроль доступа,
`/resend`, чистка телефонов по сроку.
**Без ИИ и без KV** — ИИ вторым этапом (v2), отдельным планом.
